## 1. О приложении

### 1.1. Назначение и исходное состояние

Pi Exchange — учебная копия Novčić Exchange для моделирования торговли цифровыми активами. Пользователь наблюдает рынок, управляет средствами, размещает заявки и предоставляет ликвидность. Расчёты ведутся внутри приложения; ввод и вывод тестовых токенов связывают его с локальной сетью Ethereum. Это учебный стенд, а не сервис для реальных денежных средств.

Основание анализа — однократная копия [Novcic, коммит c29c46a](https://github.com/novcic/novcic-exchange/commit/c29c46ab33c303b4c31a6bc0e22dfb5221274d63). Исходный код, история и ветка `master` сохранены. Все изменения лабораторной выполняются только в pi-exchange. Отдельные репозитории документации и торгового бота не входят в эту копию.

В исходном приложении уже реализованы регистрация, сессии, рыночные данные, счета Funding/Unified Trading, спотовые и производные инструменты, заявки, учёт движений средств, пулы ликвидности, кредитование и периодические покупки. Для лабораторной выделены восемь функций существующего ядра и два расширения на семестр. Обозначение «уже есть» означает наличие реализации и тестов в исходном коде, а не повторную приёмку работающего стенда в этой лабораторной.

Планируются экспорт истории сделок в CSV и восстановление пароля по почте. Смена пароля в авторизованном профиле уже есть, но не заменяет восстановление доступа. В этой работе не меняются backend, frontend, API и схема БД; планируемые функции описываются как будущие требования.

### 1.3. Термины

| Термин | Значение |
| --- | --- |
| Пользователь (`User`) | Зарегистрированный владелец счетов; идентификатор UUID. |
| Кошелёк (`Wallet`) | Остаток одного актива на одном типе счёта: ключ `(UserId, Kind, Asset)`. |
| Funding / Unified Trading | Счёт для хранения/ввода средств и счёт для торговли соответственно. |
| Available / Locked | Доступная и зарезервированная части остатка кошелька. |
| Инструмент (`Instrument`) | Рынок с уникальным ID; в основных примерах используется спот `BTCUSDT`. |
| Заявка (`Order`) | Поручение купить/продать актив; может исполниться несколькими сделками. |
| Сделка (`Trade`) | Исполнение между maker-заявкой из стакана и входящей taker-заявкой. |
| Стакан | Агрегированные ценовые уровни покупок и продаж без раскрытия владельцев заявок. |
| Ledger / Journal | Пользовательская история изменений остатков и журнал встречных бухгалтерских проводок. |
| Пул / LP-доли | Общие средства поставщиков ликвидности и доли участия; доходность не гарантируется. |
| Escrow | Отдельные средства ожидающего взноса; доли начисляются после его обработки. |
| Идемпотентность | Повтор одной денежной команды с тем же ключом и телом возвращает прежний результат без повторного движения средств. |

## 3. Пользовательские сценарии

Для существующих денежных команд нужны действующая авторизация и UUID `Idempotency-Key`. При неизвестном исходе клиент повторяет прежнее тело с прежним ключом. Примеры ниже — условия воспроизводимой проверки, не сведения о реальных аккаунтах и не утверждение, что запросы выполнялись в лабораторной. В каждом примере нет параллельных команд; серверные UUID и время генерируются динамически, остальные приведённые значения точны. Денежные поля JSON — строки.

### US-1. Регистрация и вход — FR-1

**Я как гость** имею email, пароль и страну, заполняю форму регистрации, затем вхожу и получаю доступ к личному кабинету.

- Вход: ещё не занятый email, пароль, допустимый код страны; для входа — реквизиты существующей записи.
- Шаги: открыть регистрацию → заполнить поля → отправить → выйти → войти с теми же реквизитами.
- Выход: создан один User; после входа доступны приватные разделы и сессия. Неверные реквизиты не дают доступ.

### US-2. Наблюдение рынка — FR-2

**Я как гость** имею выбранный инструмент, открываю рынок и получаю стакан и последние сделки.

- Вход: идентификатор инструмента, например BTCUSDT; вход в аккаунт не требуется.
- Шаги: выбрать рынок → запросить снимок → просмотреть покупки, продажи и сделки → обновить снимок после уведомления.
- Выход: агрегированные цены и количества, последние сделки; при пустом рынке — пустые списки без вымышленных сделок. Балансы не меняются.

### US-3. Просмотр остатков — FR-3

**Я как пользователь** имею действующую сессию, открываю активы и получаю остатки обоих счетов.

- Вход: авторизация; идентификатор пользователя берётся сервером из сессии.
- Шаги: открыть Assets → переключить Funding/Unified Trading → просмотреть BTC и USDT.
- Выход: Available и Locked по четырём сочетаниям счёта/актива. Отсутствующая запись представлена нулём в ответе; чтение её не создаёт.

### US-4. Перевод между счетами — FR-4

**Я как пользователь** имею доступные USDT на Funding, указываю сумму и счёт Unified Trading, подтверждаю перевод и получаю обновлённые остатки.

- Вход: сессия, актив, исходный и целевой счёт, положительная сумма, ключ команды.
- Шаги: открыть Transfer → выбрать направление и актив → ввести сумму → подтвердить → обновить баланс.
- Выход: одна завершённая команда, записи Ledger/Journal, изменившиеся остатки; общая сумма средств пользователя сохраняется.

**Конкретный пример (успех).** Funding USDT Available=500, Unified Trading USDT Available=100; Locked=0, позиций и долгов нет. Запрос `POST /api/transfer`, ключ `11111111-1111-4111-8111-111111111104`:

```json
{"asset":"USDT","from":"Funding","to":"Unified Trading","amount":"25.00000000"}
```

Ожидается HTTP 200, `message="Transfer completed."` и UUID `reference`. Funding=475 USDT, Unified Trading=125 USDT, Locked=0. Две записи Ledger имеют дельты −25 и +25 с одним reference. Повтор того же запроса и ключа возвращает тот же reference и не меняет остатки.

**Конкретный пример (ошибка).** На исходных условиях отправить `amount="600"` с новым ключом. Ожидается HTTP 400, `error="Insufficient available USDT in Funding."`. Пользователь видит ошибку; остатки остаются 500 и 100, проводок и успешной квитанции этой команды нет. Для воспроизводимой проверки отправлять запрос через API: интерфейс может остановить некорректный ввод раньше сервера.

### US-5. Размещение заявки — FR-5

**Я как пользователь** имею средства на Unified Trading и выбранный BTCUSDT, задаю сторону, тип, количество и при необходимости цену, отправляю заявку и получаю её состояние.

- Вход: сессия, Buy/Sell, Limit/Market, количество, цена для Limit, новый ключ команды; доступные средства и допустимый риск.
- Шаги: выбрать инструмент → заполнить форму → подтвердить → посмотреть заявку и исполнения.
- Выход: резерв, заявка и, при наличии контрагента, сделки с комиссиями. Фактический результат зависит от ликвидности; обещание полного исполнения отсутствует.

**Конкретный пример (успех).** Unified Trading: USDT Available=1000, Locked=0; позиций, долгов и встречных заявок нет, котировщики остановлены в тестовой фикстуре. Запрос `POST /api/orders`, ключ `11111111-1111-4111-8111-111111111105`:

```json
{"side":"Buy","type":"Limit","quantity":"0.001000","price":"50000.00","instrument":"BTCUSDT"}
```

Ожидается HTTP 200; заявка `status="Open"`, `quantity=remaining="0.001"`, `reserved="50"`. Числовые строки могут содержать завершающие нули. USDT Available=950, Locked=50; сделок и комиссии за исполнение нет. ID, Sequence и CreatedAt выдаёт сервер.

**Конкретный пример (ошибка).** На исходных условиях изменить `type` на `Market`, удалить `price`, использовать новый ключ; стакан остаётся пустым. Ожидается HTTP 400, `error="No liquidity is available for this market order."`. Новая заявка не сохраняется, USDT остаётся 1000/0, сделки и квитанция успеха не создаются. Интерфейс может сообщить отсутствие ликвидности уже на предварительной оценке; точное условие проверяется через API.

### US-6. Отмена активной заявки — FR-6

**Я как пользователь** имею свою заявку Open или PartiallyFilled, выбираю отмену и получаю освобождение неисполненного резерва.

- Вход: сессия, ID своей активной заявки и ключ отмены.
- Шаги: открыть список заявок → выбрать заявку → отменить → обновить список и баланс.
- Выход: Cancelled, Reserved=0; остаток резерва возвращается в Available. Уже совершённые сделки и комиссии не откатываются. Повторная отмена с новым ключом завершённой заявки отклоняется.

### US-7. История движений — FR-7

**Я как пользователь** имею сессию и движения средств, открываю историю и получаю последние изменения своих счетов.

- Вход: авторизация; дополнительные параметры периода у этой ручки отсутствуют.
- Шаги: открыть историю учёта → прочитать актив, счёт, причину, время и изменение суммы.
- Выход: до 100 строк Ledger по убыванию Id; пустая история — `[]`. Фильтр `AvailableDelta + LockedDelta != 0` скрывает чистое резервирование; это не полная бухгалтерская выгрузка и не история сделок FR-9.

### US-8. Взнос ликвидности и отмена — FR-8

**Я как поставщик ликвидности** имею BTC/USDT на выбранном счёте, отправляю взнос и получаю ожидающий запрос; пока он Pending, могу отменить его и получить оставшиеся активы обратно.

- Вход: сессия, sourceAccount, суммы BTC/USDT, ключ взноса; для отмены — ID запроса и новый ключ.
- Шаги: открыть Invest → Liquidity → Add liquidity → выбрать источник → задать суммы → подтвердить → просмотреть Pending → при необходимости отменить.
- Выход: средства в escrow и запрос с сохранённым источником; при активации — LP-доли, при отмене — возврат текущего состава активов. Для Unified Trading дополнительно сохраняются проверки обеспечения; Funding не расходует торговый залог.

**Конкретный пример (успех).** Funding: 500 USDT и 0 BTC; Unified Trading: 100 USDT; Locked=0. Обработка пула остановлена в тестовой фикстуре. Запрос `POST /api/liquidity-deposit`, ключ `11111111-1111-4111-8111-111111111108`:

```json
{"btc":"0","usdt":"100.00000000","sourceAccount":"Funding"}
```

Ожидается HTTP 200; `kind="Deposit"`, `status="Pending"`, `sourceAccount="Funding"`, `usdt="100"`, `btc="0"`, `shares="0"`. Funding=400 USDT, Unified Trading=100 USDT; escrow имеет 100 USDT. Повтор не списывает средства снова. Отмена через `POST /api/liquidity-cancel` с телом `{"id":"<UUID полученного запроса>"}` и новым ключом возвращает Funding=500 USDT, статус становится Cancelled; LP-доли не выдаются.

**Конкретный пример (ошибка).** На исходных условиях отправить `btc="0", usdt="0", sourceAccount="Funding"` с новым ключом. Ожидается HTTP 400, `error="Enter a positive contribution in either asset."`. Операция и успешная квитанция не создаются, Funding=500, Unified Trading=100. При серверной проверке клиент показывает ошибку; форма может заблокировать нулевой ввод заранее.

**Дополнение: отмена после частичной конвертации.** Это отдельная фикстура: до взноса Funding содержит 2000 USDT и 0 BTC, Unified Trading — 100 USDT; других операций нет. Пользователь вносит 1000 USDT из Funding. Обработчик пула размещает конверсионную заявку; до отмены реально куплено только 0.005 BTC по 50000 USDT за BTC, то есть потрачено 250 USDT. Взнос ещё Pending, доли не выданы; дальнейшие исполнения в фикстуре остановлены. Для служебного escrow комиссия за исполнение в текущей реализации не начисляется.

| Этап | Funding USDT | Funding BTC | Активы запроса в escrow |
| --- | --- | --- | --- |
| До взноса | 2000 | 0 | 0 |
| После взноса | 1000 | 0 | 1000 USDT |
| После частичной покупки BTC | 1000 | 0 | 750 USDT + 0.005 BTC |
| После отмены | 1750 | 0.005 | 0 |

Отмена с новым ключом возвращает **750 USDT и 0.005 BTC**, а не исходные 1000 USDT. Статус запроса становится Cancelled, оставшиеся конверсионные заявки отменяются, их резервы освобождаются. Unified Trading остаётся 100 USDT; LP-доли не начисляются. Уже совершённая покупка BTC сохраняется. При цене 50000 общая стоимость возвращённых активов равна 1000 USDT, но последующее изменение цены BTC меняет их оценку.

**Что видно в существующем интерфейсе:**

- В Invest → Liquidity → Liquidity requests строка показывает `From Funding`, `Cancelled`, `Not issued` и время `Closed`. Подпись `Submitted assets` относится к исходному взносу — здесь по-прежнему 1000 USDT; это **не состав возврата**. `Est. value · USD` также оценивает исходные суммы по текущему индексу, а не фиксирует выплату.
- В Assets → Funding после обновления доступны 1750 USDT и 0.005 BTC. В Balance activity видны два положительных движения с причиной `Cancelled liquidity deposit`: +750 USDT и +0.005 BTC, связанные с ID отменённого запроса.
- Отдельного поля с составом возврата в строке Liquidity requests сейчас нет. Документ описывает фактический интерфейс, не обещая ещё не реализованную детализацию.

Основание: тест `LiquidityFundingCancellationReturnsConvertedAssetsToFunding` в [LiquidityFundingTests.cs](../tests/Novcic.Tests/LiquidityFundingTests.cs), методы `CancelLiquidity` и `ChargeExecutionFee` в [LiquidityEngine.cs](../src/Novcic.Core/LiquidityEngine.cs), отображение в [LiquidityPanel.tsx](../web/src/LiquidityPanel.tsx) и [Assets.tsx](../web/src/Assets.tsx). Это проверяемый пример по коду, не запись реального пополнения.

### US-9. Выгрузка сделок — FR-9 · планируется

### 4.1. Границы точности моделей

- В модели данных у User показаны связи обычного владельца. Служебные акторы AMM/escrow могут использовать UserId без строки в auth.Users. Во всей текущей EF-модели отсутствуют FK; каскадное удаление пользователей из диаграммы не следует.
- Trade содержит MakerOrderId/TakerOrderId и BuyerId/SellerId. Заявка может участвовать в нескольких исполнениях в каждой из ролей, но у сделки ровно по одной заявке maker и taker. Две отдельные связи User–Trade подписаны «покупатель / BuyerId» и «продавец / SellerId». Один User может участвовать в 0..* сделках в каждой роли; у каждой сделки соответствующая запись User имеет кратность 0..1, поскольку служебный актор может отсутствовать в auth.Users. Это не означает nullable для BuyerId/SellerId: сами идентификаторы обязательны. Все связи остаются логическими, без физических FK; число сущностей по-прежнему равно пяти.
- Деятельность и состояния детализируют спот. Проверка риска может откатить всю команду после SaveChanges, но до Commit. Промежуточные состояния внутри транзакции не обязательно наблюдаемы клиентом; отклонённый до Commit запрос не создаёт сохранённого состояния Rejected.
- Для события Cancelled возможны отмена пользователем, защита от самоторговли или отмена неисполненного рыночного остатка. Повторное изменение Filled/Cancelled новым запросом отмены запрещено. Отмена не стирает исполненную часть.
- История Ledger и межсервисные зависимости описаны отдельно: ограничение в пять сущностей не означает, что остальные таблицы отсутствуют.

### 4.2. Воспроизводимость и ревью

Экспорты строятся локально PlantUML **1.2026.9** с Graphviz; инструкции — [diagrams/README.md](diagrams/README.md). Проверка комплектности: `python scripts/check-lab2.py`. Проверка неизменности публичного контракта: `python scripts/check-contract.py`.

Автор открывает PR `lab-2 → main`. Федоров Арсений проверяет модель данных и согласованность учёта; Андрей Самохвалов — сценарии и взаимодействие. Каждый оставляет минимум один содержательный комментарий к конкретному месту, затем после ответа/исправления — approve. Автор отвечает на каждый комментарий; исправления оформляет отдельными коммитами. Только после двух реальных одобрений, закрытия обсуждений и успешных проверок выполняются merge и тег `lab-2`. Наличие версии документа 1.0 само по себе не означает завершённое командное ревью.
