## 1. Назначение и связь с требованиями

Операцию вызывает форма Transfer в клиенте либо авторизованная программа пользователя. Она переносит доступные BTC или USDT между счетами Funding и Unified Trading одного пользователя. Общая сумма актива сохраняется, комиссия за этот перевод не взимается.

Связанные материалы лабораторной № 2:

- **FR-4** — перевод доступных средств между своими счетами: [функциональные требования](01-requirements.md#21-функциональные-требования).
- **US-4** — пользователь задаёт актив, направление и сумму и получает обновлённые остатки: [сценарий перевода](01-requirements.md#us-4-перевод-между-счетами--fr-4).
- [Диаграмма последовательности перевода](diagrams/transfer-sequence.png).

## 2. Как вызвать операцию

Отправить HTTP POST на `{BASE_URL}/api/transfer`, где `BASE_URL` — адрес API вашего учебного стенда без завершающего `/`. В примерах `api.example.test` — заменяемый адрес, а не действующий сервер проекта.

| Заголовок | Обязательность и значение |
| --- | --- |
| `Authorization` | Для выбранного здесь способа входа обязателен: `Bearer <ACCESS_TOKEN>`, действующий JWT пользователя |
| `Content-Type` | `application/json` |
| `Idempotency-Key` | Обязательный UUID; отдельное значение для каждой новой команды |

Токен берётся из поля `accessToken` ответа входа `POST /api/auth/login` с JSON `{"email":"<ваш email>","password":"<ваш пароль>"}`. Пользователь должен уже иметь учётную запись на выбранном стенде. Токен и пароль нельзя помещать в коммиты или комментарии PR.

В проекте также есть подписанные API-ключи; эти примеры используют только Bearer-токен, поэтому заголовок `X-Api-Key` передавать не нужно. Идентификатор пользователя берётся из проверенного токена. Поле `userId`, внутренний URL matching-сервиса и служебный `X-Internal-Key` вызывающей стороне не нужны.

### Тело запроса

JSON-объект без внешней обёртки. Все четыре поля обязательны для корректного вызова.

| Поле | Тип в примерах | Допустимые значения |
| --- | --- | --- |
| `asset` | string | Ровно `BTC` или `USDT` |
| `from` | string | Ровно `Funding` или `Unified Trading` |
| `to` | string | Те же значения; должно отличаться от `from` |
| `amount` | string с десятичным числом | Больше 0, не больше `1000000000`, не более 8 знаков после десятичной точки; например, `"25.00000000"` |

Регистр значений и пробел в `Unified Trading` значимы. На сервере сумма имеет тип `decimal`. JSON-настройки допускают и числовое значение, но в этом контракте передаём сумму строкой с точкой без разделителей тысяч, чтобы клиент не вносил погрешности двоичной арифметики.

### Условия выполнения

- На исходном счёте достаточно **доступных**, а не заблокированных средств выбранного актива.
- При переводе из Unified Trading в Funding должно сохраняться допустимое обеспечение открытых позиций и обязательств. При наличии риска операция может быть отклонена, даже если доступный остаток достаточен.
- Итоговый остаток должен помещаться в поддерживаемый диапазон БД; сервер также проверяет верхнюю границу баланса.
- Для двух примеров ниже используем отдельного учебного пользователя без позиций, долгов и параллельных операций; оба счёта имеют `Locked=0`.

## 3. Результат и повтор запроса

**Успех:** HTTP **200**, `Content-Type: application/json` (возможен параметр `charset`), JSON-объект:

| Поле | Тип | Значение |
| --- | --- | --- |
| `reference` | string, UUID | Сгенерированный сервером идентификатор перевода |
| `message` | string | `Transfer completed.` |

Ответ не содержит новые остатки. Клиент может запросить их через `GET /api/balances` с тем же Bearer-токеном. Сумма списывается с доступного остатка `from` и зачисляется на `to`, `Locked` не меняется. Две записи Ledger имеют дельты `-amount` и `+amount` и общий `reference`; проводки Journal, остатки и успешная квитанция Receipts сохраняются одной транзакцией.

**Выбранная характерная ошибка:** при недостатке доступных USDT на Funding возвращается HTTP **400**, JSON `{"error":"Insufficient available USDT in Funding."}`. Поле `error` имеет тип string. Изменения команды откатываются: частичного перевода, новых проводок и успешной квитанции нет. Для другого актива или счёта соответствующие слова в сообщении меняются.

Это не единственная возможная ошибка: недопустимые параметры и нарушения правил также дают 400; отсутствующий или недействительный токен — 401. Формат тела ошибки 401 не следует считать таким же, как у описанной ошибки 400.

Ключ повторения действует в пределах пользователя. После успешного выполнения повтор с **тем же ключом и тем же содержимым** возвращает сохранённый ответ, включая прежний `reference`, без нового списания. Если успешный ключ используется с другим содержимым, сервер отвечает HTTP 400: `{"error":"This idempotency key was already used for a different request."}`. При потере ответа повторяют исходную команду с прежним ключом; новый ключ означает новую команду. Неуспешный перевод не сохраняет успешную квитанцию.

## 4. Пример успешного вызова

**Начальное состояние:** Funding — 500 USDT, Unified Trading — 100 USDT; средства доступны, `Locked=0`. Указанный ниже ключ ещё не использовался этим пользователем.

```http
POST /api/transfer HTTP/1.1
Host: api.example.test
Authorization: Bearer <ACCESS_TOKEN>
Content-Type: application/json
Idempotency-Key: 11111111-1111-4111-8111-111111111104

{"asset":"USDT","from":"Funding","to":"Unified Trading","amount":"25.00000000"}
```

**Ожидаемый ответ:** HTTP 200, например:

```json
{"reference":"33333333-3333-4333-8333-333333333304","message":"Transfer completed."}
```

Значение `reference` здесь иллюстративное: фактический UUID сформирует сервер. Проверяют его формат и сохранение при повторе, а не совпадение с этим числом.

**Итог:** Funding — **475 USDT**, Unified Trading — **125 USDT**, `Locked=0`. Две записи Ledger: −25 и +25 USDT. Повтор исходного запроса с тем же ключом оставит эти остатки без изменений.

## 5. Пример ошибки

**Начальное состояние заново:** Funding — 500 USDT, Unified Trading — 100 USDT, `Locked=0`. Это независимый пример, а не продолжение успешного перевода. Используйте отдельного подготовленного пользователя либо восстановленную учебную фикстуру; ключ ещё не использован.

```http
POST /api/transfer HTTP/1.1
Host: api.example.test
Authorization: Bearer <ACCESS_TOKEN>
Content-Type: application/json
Idempotency-Key: 22222222-2222-4222-8222-222222222204

{"asset":"USDT","from":"Funding","to":"Unified Trading","amount":"600"}
```

**Ожидаемый ответ:** HTTP 400:

```json
{"error":"Insufficient available USDT in Funding."}
```

**Итог:** остатки остаются **500 и 100 USDT**; новых записей Ledger/Journal и успешной квитанции этой команды нет. В клиентской форме сумма может быть отклонена до отправки; для проверки ответа сервера нужен непосредственный вызов API.

## 6. Те же вызовы из PowerShell

Команды рассчитаны на Windows PowerShell 5.1 или PowerShell 7. Подготовьте исходные остатки из соответствующего примера на учебном стенде: команды ниже их не создают и не сбрасывают. Впишите свой адрес и действующий токен в локальной сессии. Не публикуйте токен в результатах проверки.

Общая подготовка:

```powershell
$baseUrl = 'https://api.example.test' # Заменить адресом своего учебного API без / в конце
$accessToken = '<ACCESS_TOKEN>'     # Заменить действующим токеном учебного пользователя
$headers = @{ Authorization = "Bearer $accessToken" }
```

Успешный пример:

```powershell
$headers['Idempotency-Key'] = '11111111-1111-4111-8111-111111111104'
$body = '{"asset":"USDT","from":"Funding","to":"Unified Trading","amount":"25.00000000"}'
$response = Invoke-WebRequest -UseBasicParsing -Method Post -Uri "$baseUrl/api/transfer" -Headers $headers -ContentType 'application/json' -Body $body
[int]$response.StatusCode # 200
$response.Content        # JSON с reference и message
```

Пример ошибки, после подготовки его независимых исходных условий и токена соответствующего пользователя:

```powershell
$headers['Authorization'] = "Bearer $accessToken"
$headers['Idempotency-Key'] = '22222222-2222-4222-8222-222222222204'
$body = '{"asset":"USDT","from":"Funding","to":"Unified Trading","amount":"600"}'
try {
    $response = Invoke-WebRequest -UseBasicParsing -Method Post -Uri "$baseUrl/api/transfer" -Headers $headers -ContentType 'application/json' -Body $body -ErrorAction Stop
    [int]$response.StatusCode
    $response.Content
} catch {
    if ($null -eq $_.Exception.Response) { throw } # Например, сервер недоступен
    [int]$_.Exception.Response.StatusCode         # Ожидается 400
    $_.ErrorDetails.Message                      # JSON с error
}
```

Фиксированные ключи нужны для понятных примеров. При новой независимой проверке используйте новые UUID; при проверке повторной доставки сохраняйте прежний ключ.
